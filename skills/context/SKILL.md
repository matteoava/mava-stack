# Context

Give the next task, person, or agent an accurate starting point: what matters, what changed, what is reliable, and what happens next. Maintain useful shared knowledge without creating a competing project record.

## Uses

Read the applicable instructions below before acting.

- [ORCHESTRATE.MD shared execution rules](../../ORCHESTRATE.MD#shared-execution-rules): reading, evidence, safe saves, and authority.
- [memory/README.md](../../memory/README.md): store boundaries and contribution rules.
- initialize-stack when a folder is not bootstrapped. search for broad resource discovery, reconcile for a systematic plan-versus-artifact review, and [storyline](../storyline/SKILL.md) for a formal handoff document or deck.

## Choose the operation

- **Brief:** assemble context for a question or decision. It is read-only unless the user asks for a save.
- **Refresh:** incorporate new evidence into authorized shared context under standing capture authority. memory/dreaming-lw.md runs this nightly.
- **Handoff:** reconstruct the activity and its last evidenced checkpoint for another session, agent, or teammate.

Combine operations when the request calls for it.

## 1. Resolve the initiative and task

- Read the local AGENTS.md, the canonical MEMORY.md it references, and existing activity records. Use the working profile for configured sources and authority, and do not repeat environment setup.
- Establish the objective, audience, decision, activity ID, current phase, and intended output.
- When one message discusses several initiatives, keep their facts, owners, priorities, and memories separate.
- If the folder is not bootstrapped, brief from available evidence, name the missing setup, and route bootstrap to initialize-stack. Never create a new record set silently.

## 2. Retrieve what matters

- Start from shared memory and the current plan, then open the original sources this task needs. Follow pointers rather than loading every customer file.
- Read documents, decks, workbooks, notes, and team edits with format-aware tools, and use the current human-edited version.
- Search email, meeting summaries, and team discussions through the selected connectors within the permitted scope. Read enough of each thread to catch replies and corrections.
- For a refresh, bound retrieval by changed files, supplied feedback, and prior coverage instead of rescanning everything. Include replies to earlier discussions when they matter.
- Track source identity, version, author, effective date, and inspection date. A metadata match is not inspected content.
- Deduplicate forwards, attachments, meeting summaries, and prior AI syntheses that derive from the same evidence.
- Report unavailable connectors, unreadable files, missing attachments, search windows, and partial pagination. Missing evidence does not prove that an event or artifact does not exist.

## 3. Build a faithful current view

- Keep source statements, interpretation, assumptions, proposals, authorized decisions, and observed outcomes apart. When extracting feedback, record what was said before interpreting it.
- Keep source roles clear. Approved scope is a baseline, a session deck frames a discussion, notes and summaries report it, and another customer's artifact only illustrates structure; never import its facts.
- For each meaningful change, identify the affected scope, phase, requirement, decision, artifact version, owner, or dependency, and its actual disposition: proposed, agreed, under investigation, backlog, excluded, or completed only where supported.
- Resolve conflicts by authority, applicability, and evidence, not recency. Leave unknown rationale or ownership explicit.
- Separate reported progress from verified completion. Flag a stale tracker without creating duplicate assignments.
- List downstream effects on requirements, architecture, estimates, decks, SoW, and delivery plans as pending alignment, not as completed updates.
- A newer message never silently amends an approved baseline. Record the proposed change; consequential decisions and substantive document changes stay with their owner and workflow.
- Verify changing product or commercial claims against current primary sources. Distinguish conceptual demonstrations, inspected configuration, runtime evidence, and business outcomes.

## 4. Maintain the right records

Save only within the request or an existing maintenance mandate. A read-only brief writes nothing.

| Record | Maintain here |
| --- | --- |
| Shared MEMORY.md | Concise current knowledge, corrections, lessons, open questions, source pointers, and handoff context, organized by topic or workstream. |
| Local AGENTS.md | Stable initiative or folder context, valid navigation and memory paths, and agreed standing guidance, kept below 200 lines. |
| Existing plan or authoritative artifact | Its own state, only within the task's edit authority. Otherwise flag the needed update for its owner. |
| Private LONG_TERM_MEMORY.md | A durable lesson or shared-record pointer, only when personal capture is configured and authorized. |

- Update sections in place with source and version references, verification dates, uncertainty, the contributor, and the observed timestamp. Label unknown identity.
- Preserve the initialization record. It records provenance; it does not limit later content.
- Keep superseded baselines referenced but not presented as current, and record the reason for meaningful corrections.
- When later refreshes depend on it, keep the last checked scope and time in existing shared records.
- Keep updates appropriate to the team's access, and label private links teammates cannot open. Keep personal configuration, private reflections, and unrelated initiatives out.
- Do not create CONTEXT.md, another index, a chronological activity dump, or copies of sources. Use native host memory as a lead to verify, never rewrite it. The public LONG_TERM_MEMORY.md stays empty.
- Save under the shared safe-save rules. If a conflict cannot be resolved, return the proposed update and name the affected record. Avoid duplicate no-change entries. After a partial save, report exactly what saved and resume without replaying completed changes.

Preserve the activity ID, baselines, owners, and progress. Never reset the workflow, infer a missing approval, or mark a handoff complete just because a summary exists.

## Output and completion

Return a context pack sized to the next task:

- **Current basis:** objective, audience, phase, and the relevant approved baselines and artifact versions.
- **What changed:** supported findings, interpretations, conflicts, and affected downstream work.
- **Next checkpoint:** the action or waiting input, its owner, and the event that resumes it. Keep unknown owners or dates explicit.
- **Evidence and coverage:** usable source references, freshness, inspection limits, and open questions.
- **Saved changes:** the records actually updated, or confirmation that the brief was read-only, including any partial-save gaps.

A chat response is enough unless a saved handoff is requested or an existing record needs maintenance. The work is complete when the next task can proceed from a traceable current view, or when the blocking gap and its owner are clear.

Context does not turn into a search or reconciliation exercise automatically, and it does not create schedules, monitoring, or messages.
