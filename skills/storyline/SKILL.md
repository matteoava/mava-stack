# Storyline and artifact production

Help the audience understand the situation, evidence, options, recommendation, and next decision through graphical, readable material built on an existing editable artifact. Other skills supply content and validation needs; this skill owns production.

## Uses

Read the applicable instructions below before acting.

- search, or the host's equivalent tools, for authorized prior work across customers and projects.
- [Principle 9](../../PRINCIPLES.md#9-deliver-strong-decision-material) and the [ORCHESTRATE.MD shared execution rules](../../ORCHESTRATE.MD#shared-execution-rules).
- The working profile's production route, plus format-specific editing and rendering tools or a configured delegation route.

## 1. Establish the task

- Read the initiative guidance, shared memory, the request, authoritative sources, and current artifact versions. Identify the audience, decision, purpose, stage, format, destination, and production route.
- Decide whether this is a content brief, a new deliverable, or a revision of an existing artifact. If the user wants to discuss structure first, do that before producing a file.
- Explain meaningful narrative and production choices step by step, and report the understanding state; approval of a presentation is not confirmed understanding. Ask only for missing essentials, and let routine understood production proceed.

## 2. Find and choose the base

Before producing a new deck or formal document, search authorized prior work across customers and projects. Inspect promising originals rather than filenames or snippets, and record the search coverage and access gaps.

Keep three roles separate:

| Role | Use |
| --- | --- |
| Editable base | The actual deck or document to copy for its structure, theme, layouts, styles, and reusable composition. |
| Composition reference | Arguments, visual patterns, diagrams, or examples to adapt selectively. It does not define the target's layout or facts. |
| Authoritative source | Current initiative scope, architecture, estimates, decisions, and evidence that establish the target content. |

- Respect a supplied base. Otherwise choose the best editable base automatically, weighing audience, purpose, structure, format, visual quality, and reuse limits, and explain why. Ask only when material uncertainty blocks a sound choice.
- Prefer neutral templates when they fit. Use customer artifacts only within their reuse and audience limits; access is not sharing clearance. Keep the requested baseline even if another file looks newer.
- **No usable base:** prepare the content brief, report the search coverage and the precise gap, and ask the user for a reference before producing the file. Never fall back silently to a blank document to hide missing access or editing capability.

## 3. Build the narrative and adaptation map

- Lead with the audience's question and a coherent answer: context, problem or opportunity, evidence, options, recommendation, implications, and next decision. Use only the structure this purpose needs, not a generic framework checklist.
- For each slide or section, define the main message (as its title where possible), supporting facts, a useful visual or table, and the reader's action. Keep implementation internals out unless they help the decision.
- Map the messages to existing slides, sections, layouts, and assets, deciding what stays, what gets new content, and where a new slide or section is genuinely needed.
- Keep scope, estimate scenarios and versions, assumptions, approval states, and numerical provenance intact.
- Keep source-to-claim traceability in working notes. Show citations where useful or required, and keep any required attribution visible; choose another asset if its terms cannot be met.

## 4. Copy and adapt

- **New deliverable:** make an actual copy of the base in the agreed destination, edit the copy, and preserve the original. Follow existing file and version conventions.
- **Revision:** start from the current human-edited artifact and keep its latest changes. Do not switch bases between iterations. Honor an explicit request to edit in place by using recoverable version history.
- Record the target revision before editing. Before replacing a shared file, recheck its revision, then merge intervening edits or report the conflict and keep the proposed copy. Check that the destination has not appeared in the meantime.
- Keep masters, layouts, page size, styles, fonts, colors, headers and footers, and tables, and replace content through existing placeholders and styles.
- Make the smallest layout change that keeps content readable and correct. Duplicate a suitable slide, layout, or section to add material rather than shrinking text.
- Remove inherited pages the argument does not need, and explain meaningful departures from the base.
- Clean inherited material: customer facts, examples, contacts, dates, commitments, numbers, speaker notes, comments, hidden slides and sheets, embedded objects, links, tracked changes, and document properties. Never import reference-customer facts as target evidence or silently amend approved baselines.
- Use the configured production route and do not assume a particular application. If a tool cannot preserve the editable structure, use another supported route or report the limit. A text extract or screenshot reconstruction does not prove the layout survived.

## 5. Make visuals carry the explanation

- Prefer informative diagrams, journeys, comparisons, charts, screenshots, and supporting icons over dense text where they explain better. Graphics show relationships or evidence, not decoration.
- Reuse the base's layouts, visual language, and suitable existing assets first. When an asset is missing, search online with public, non-sensitive queries for original or official screenshots, icons, or images.
- Check each asset's source, version or date, relevance, resolution, and reuse and attribution terms. Prefer originals to reposts, and record provenance. Public availability is not permission.
- Screenshots must be authentic and match the claimed product and version. Never fabricate one or present a mockup as real behavior, and label conceptual visuals. If no trustworthy screenshot exists, report the gap and use a clearly labeled alternative or request a capture.
- Keep diagrams faithful to real behavior, including branches, loops, controls, and handoffs. Keep chart data, units, and calculation basis, and keep visuals editable with alt text where supported.

## 6. Verify and deliver

- Open and render the finished copy. Inspect every slide or page for fit, clipping, readability, alignment, hierarchy, image quality, table breaks, and pagination, then fix and re-render.
- Check facts, calculations, terminology, baseline and version references, scope and approval wording, links, page numbers, contents fields, notes, hidden content, and metadata. Content verification, file integrity, and visual inspection are separate evidence.
- If rendering or a check is unavailable, state what was inspected and leave that validation open. Do not claim a file opens or the layout survived based on extraction alone. Inspect delegated results yourself rather than forwarding a completion report.
- Deliver the editable artifact and any requested exports, with the base used and why, material changes, checks performed, remaining gaps, and the next decision. An outline counts only as an intermediate result when a full artifact was requested and a route exists.
- Keep sources and final outputs separate from temporary copies, render previews, and scratch files, and remove the temporary material after verification. Do not create generic output folders.

Saving an artifact does not authorize sending, publishing, or approving its content on the user's behalf.
