# Prepare a session

Make the next discussion useful: what participants need to understand, what must be decided or learned, and how the results will move the initiative forward.

## Uses

Read the applicable instructions below before acting.

- [ORCHESTRATE.MD shared execution rules](../../ORCHESTRATE.MD#shared-execution-rules) and [principle 7](../../PRINCIPLES.md#7-explain-until-the-user-understands).
- context or search to assemble prior material, [storyline](../storyline/SKILL.md) for any deck or formal document, and requirements for consolidating the answers afterwards.

## 1. Establish the session and current position

- Read the local AGENTS.md, shared MEMORY.md, existing plan, relevant requirements, agreed scope, architecture, and prior session records. Use authorized folder and communication sources, and report missing access or attachments instead of guessing their contents.
- Identify the session type, objective, audience and domain familiarity, participants and decision roles, expected outputs, and duration.
- Preserve the existing activity and phase. Do not repeat a completed kickoff or reopen an agreed decision without a reason.
- Ask only about gaps that remain after inspection. Explain the proposed flow and refine it through feedback.

## 2. Match the session to its purpose

| Session | Prepare around |
| --- | --- |
| Presales discovery | Customer context, current process and pain points, actors, desired outcomes, value measures, current systems and data, constraints, assumptions, priority questions, and the evidence needed before recommending scope. |
| Delivery kickoff | Agreed scope and exclusions, outcomes, architecture overview, phases, responsibilities, customer prerequisites, dependencies, review and acceptance arrangements, risks, communication boundaries, and the next checkpoint. |
| Solution design | Decisions and scope agreed so far, a walkthrough of the current solution, precise process, data, action, and control questions, exceptions and dependencies, candidate tailoring, acceptance examples, and open feasibility or scope choices. |

- Explain product basics only to the depth this audience needs. Distinguish documented capability, inspected configuration, runtime observation, proposed extension, and unknown behavior, and verify changing product facts against current primary sources.
- Explain the whole customer journey before detailed components. A reusable component is not the full journey, and a conceptual demo is not proof of runtime behavior.

## 3. Build the discussion flow

Open with the purpose and the decision or learning needed. Recap only the relevant current basis, walk through the process or solution, explore the important questions, and close with decisions, open items, owners, and next inputs.

Use the known duration for realistic time boxes. If the duration is unknown, mark the timing as proposed. Keep facilitator notes separate from audience-facing content where that helps.

For each important discussion point, define:

- The source, requirement, decision, or assumption it relates to.
- What participants need to understand before answering.
- A precise question or choice, with a concrete scenario where useful.
- The expected kind of answer: example, threshold, rule, input and output, owner, exception, or acceptance criterion.
- Who can answer or decide, and what later work depends on it.

Avoid a generic questionnaire when context already has the answer. For uncertain points, keep a targeted validation question; never quietly turn an assumption into a customer requirement.

## 4. Prepare the materials

- Create only what the request needs: an agenda, facilitator notes, a pre-read, a deck brief, or the actual presentation or document.
- A deck brief gives each slide's message, discussion purpose, useful visual, source basis, and the question or decision it serves.
- Produce any deck or formal document through storyline: search prior work across customers and projects, choose and copy the best editable base, adapt it with minimal layout change, and validate. Respect a supplied base, and revise the current human-edited version.
- Keep slides graphical with existing visuals or sourced screenshots, diagrams, charts, or icons through storyline. Never invent a product screenshot or default to a text-only deck.
- If no usable base exists, deliver the content brief and the search gap, and ask for a reference before producing the file.
- When production is requested and the configured route works, deliver the file rather than an outline. If editing, rendering, or access fails, deliver what is supported and state exactly what remains.

## 5. Design capture and handoff

- Define a lightweight way to capture answers against the questions, with source, participant, and date, decision authority, scope disposition, open points, owner, and next trigger. Reuse existing records; create a capture aid only when the session needs one.
- Keep current scope, proposed changes, investigation, backlog, and exclusions distinct. Business approval, technical permissions, and ordinary user confirmation are different things; capture what is actually needed without inventing controls or agreement.
- Prepare a closing recap that participants can correct. Afterwards, requirements consolidates the answers and context maintains shared knowledge.
- Never mark planned questions as answered, a prepared deck as a held session, or a proposed decision as approved.

## Completion and boundaries

Return the session purpose and current basis, the proposed flow, priority questions and decision roles, the materials actually prepared and validated, the capture approach, dependencies, the understanding state, and the next useful action.

Delivery preparation stays within architecture oversight and coordination; implementation and runtime execution remain with their contributors. Sending invitations or messages, scheduling meetings, changing commitments, and amending approved scope need their own authority.

Save materials only in the initiative's existing appropriate location, preserve source files and human edits, and remove task-created temporary material.
